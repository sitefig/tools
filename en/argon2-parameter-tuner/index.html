Argon2 Parameter Tuner

Enter a target time per hash, a memory budget and your core count, and get suggested Argon2id memory, iterations and parallelism. It is a calculator and does not run Argon2 itself.

Use the tool

Why this tool exists

Argon2 is only as strong as its settings. Too little memory and an attacker with GPUs can try passwords quickly; too much and a burst of logins exhausts your server. Guidance such as the OWASP recommendations gives starting points, but the right numbers depend on your hardware and how many people sign in at once.

This tuner turns your constraints into parameters. You say how long a hash may take, how much memory one hash may use, how many cores you have and how many concurrent logins you must survive. You supply a measured throughput figure from your own stack, because this page cannot benchmark your server. Treat the result as a starting point and test it under load.

How to use it

  1. Enter the target time per hash in milliseconds and the memory budget in MiB.
  2. Set the parallelism and the number of CPU cores available for each hash.
  3. Enter the throughput you measured by timing one hash in your own stack, and the number of concurrent logins to support.
  4. Read the suggested iterations and memory use, then test them on your real server.

Frequently asked questions

Does this tool run Argon2?

No. It only calculates. The throughput value you enter stands in for your hardware, so measure one hash in your own language and server, then use that figure to calibrate the suggestions.

Why Argon2id?

Argon2id mixes data-dependent and data-independent memory access, which resists both GPU cracking and side-channel attacks. It is the variant most guidance recommends for password hashing.

What does the concurrent logins setting do?

It multiplies the memory per hash by the number of simultaneous sign-ins, so you can see whether a login spike would exceed your server's memory. Lower the memory cost or rate-limit logins if it would.
